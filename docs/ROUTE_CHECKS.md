# Pons V2 native-ETH buy/sell adapter

This adds a read-only route assessment to Telegram paper plans. Open `/snipes`, select a draft or armed plan and press **Test buy + sell**. It requires an enabled project, chain collection, one fresh owner-reviewed exact mainnet identity and its matching deployer. A manual test never arms a plan or authorizes a live transaction. A new policy-v2 plan, once separately armed in Telegram, requires a fresh matching result before its one automatic paper entry. Existing immutable version-1 plans retain their original reference-price policy.

## What is implemented

- Bind mainnet 4663 and the reviewed token/deployer to `getLaunchedToken` on the pinned Pons V2 factory. Reject unknown deployments, non-native quote assets and graduated routes.
- Check the exact deployed factory bytecode fingerprint. Check curve/token runtime fingerprints generated from explorer-verified source, masking only Solidity constructor immutable positions; independently check curve factory/token, 18 decimals and a non-exempt, empty hypothetical wallet.
- Pin a fresh block, simulate a buy to obtain the actual quantity, then independently simulate buy → balance check → exact approval → sell → empty balance check against the same parent block and simulated timestamp (parent time plus one second). Reject a currently active launch-tax window: the simulator's next-second timestamp must not quietly underquote a tax that could apply to same-second Arbitrum execution. Only the hypothetical wallet's ETH balance is overridden. No token balances, allowances, curve state, exemptions, tax windows or deployed code are altered.
- Require successful calls, exact balances and matching trade event amounts. Record fees including launch tax, creator tax, immediate sell proceeds, round-trip loss, execution gas units and a gas-price estimate. Reject partial fills, graduation during the buy, reverted exits, mismatched amounts and block reorgs.
- Construct unsigned buy/approval/sell calldata with bounded output amounts. These target the hypothetical wallet and are diagnostic artifacts, **not broadcast-ready user orders**. The curve ABI has no deadline parameter; report expiry is an off-chain freshness limit, not an on-chain transaction deadline.
- Persist results and show them in Telegram. A report is fresh for at most 60 seconds from the parent block. Historical results are clearly labeled. Repeated callbacks and automatic policy-v2 retries are limited to once per plan per five minutes; at most three plan checks can be requested globally in that window. The worker has durable leases and request expiry. Every production RPC call passes the existing pause/cooldown/daily-cap guard; one assessment has a hard ceiling of 20 requests. Idle queues use no RPC. Provider compute-unit billing can differ from request counts.
- Bind every report to the immutable plan, reviewed source hash, reviewed deployment transaction/block and request timestamp. Settlement rechecks the current identity, report age, exact token/deployer/budget/price ceiling, route version and binding inside the serialized paper-book transaction.
- For policy-v2 entries, record the simulated quantity and buy fees/tax. Require estimated buy execution gas to fit the Telegram-approved allowance, then charge the full allowance to paper cost. This is deliberately conservative and does not claim the estimate was actually paid. The total round-trip gas estimate remains diagnostic and excludes L1 data fees.

## Remaining execution work

Policy-v2 paper entries consume fresh route quantities/fees and account for an approved entry gas allowance. Manual exits from those positions use two fresh canonical-block checks: one for the Telegram preview and one after approval. The exact Pons reserve impact, base fee and creator tax settle the fill; the second quote must satisfy the preview minimum. Exit gas is still excluded. Existing version-1 positions retain the fixed reference-price model. Native curves alone are insufficient: ETH budget plans need another adapter when a token trades against an ERC-20 or has graduated to V4.

The simulation excludes future price movement, transaction ordering, pending transactions and L1 data fees. It funds an otherwise empty hypothetical wallet and skips signature/normal transaction validation; it does not prove the user's funding, nonce, gas budget or signer readiness. Successful immediate resale does not guarantee a later exit. Isolated signing, live policy enforcement, nonce/receipt recovery, actual funding and automated exit policies remain unimplemented. Keep both live flags false.
